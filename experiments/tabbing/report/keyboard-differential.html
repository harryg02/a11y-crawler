The Keyboard Differential

Twelve detectors for clickable-but-not-keyboard-reachable elements, scored in eighteen configurations against a purpose-built corpus with known answers. The behavioural oracle wins by a wide margin — and three of the survey's claims do not survive contact with a browser.

What was measured

The survey in tabbing.md ranks methods by published evidence. This runs them.

Nine fixture pages carry 60 labelled probes: the canonical defect (a <div> with addEventListener('click') and no tabindex), plus the variants the survey names — delegated listeners, React handlers, hover-only menus, closed shadow roots, handlers that touch nothing but fetch or localStorage, and a deliberate set of decoys that look operable and are not.

Ground truth lives in a separate manifest, keyed by probe id, so no detector can read it. A probe counts as a violation only when all three hold: a real user can operate it with a mouse, cannot operate it with a keyboard, and the same functionality is not reachable from some other keyboard-reachable element.

Set T — the true tab order — is computed once per page by dispatching real Tab keypresses through CDP and reading document.activeElement, piercing shadow roots and frames. Every candidate generator reports candidates minus T.

STAGE 1
Set T, exactly
Real Tab dispatch. Free, exact, and immediately useful on its own.
STAGE 2
Over-generate candidates
Listeners, properties, CSS, lexicon. 32–292 ms for the whole corpus.
STAGE 3
Behavioural confirmation
Mouse vs keyboard, eight state channels, full reload between. 1.20 s per probe.
STAGE 4
Equivalence dismissal
Drop a finding when a keyboard-reachable element runs exactly the same functions.

Three corrections to the survey

Each of these changes what a real implementation should do.

React 19 handlers are directly inspectable

tabbing.md §1.2 and §3.6

“React attaches a single listener at the root container. getEventListeners on a React button returns nothing. … Framework-prop extraction is not an optimization here — it is mandatory.”

It returns a click listener. React 19 does install 139 listeners on the root container — three of them click — but it also assigns element.onclick directly on every element carrying an onClick prop — the property, not the attribute. CDP getEventListeners reports that assignment, and found both React defects in the corpus. A three-line typeof el.onclick === 'function' check finds them too.

Framework-prop extraction is still the only route to which prop was bound, and stays necessary for other frameworks. It is not the only route to that a handler exists, and building a version-fragile React adapter for that purpose is wasted work.

The addEventListener shim is the weakest listener route, not the strongest

tabbing.md §3.5

“Inject before any app script … and record every registration. … Blind to anything registered before injection.”

Blind to considerably more than that. Measured at 65.4% recall, the worst of the three listener routes, and it misses three whole classes that have nothing to do with injection timing: React (property assignment, never calls addEventListener), inline onclick= attributes, and delegated listeners bound to document.

Its real value is the one the survey mentions in passing and undersells: the stack trace. Every finding came out with the exact file and line that registered the handler, which is the difference between a triageable report and a muted one.

There is no such thing as clicking without hovering

tabbing.md §3.9

“Probing click alone would have missed 35 of 49.”

A trusted click cannot skip the hover: CDP dispatches a mousemove to the target coordinates before mousePressed, so any prober using real input has already triggered :hover by the time the button goes down. The first version of this experiment scored a “click-only” arm identically to the hover arm for exactly that reason — the ablation was measuring nothing.

The real variable is the observation window. Reading state while the pointer rests on the element caught the pure-CSS hover menu; parking the pointer first lost it and gained back a false positive on a hover tooltip. On this corpus that trade is worth +1 true positive for −1 false negative — real, but nothing like the 35-of-49 headline. That number describes tools driving element.click(), which fires no pointer events at all.

The one that decides the whole design

Stage-4 equivalence dismissal has a threshold, and it is not a soft one.

Stage 4 drops a confirmed finding when some keyboard-reachable element produces the same effect — a clickable card wrapping a real link, a styled label driving a focusable checkbox. The survey proposes comparing executed-function sets. It does not say how close is close enough, and that turns out to be the entire question.

Similarity thresholdTPFPFNPrecisionRecallF1
Jaccard ≥ 0.50231395.8%88.5%92.0%
Jaccard ≥ 0.80231395.8%88.5%92.0%
Jaccard ≥ 0.95231395.8%88.5%92.0%
Exact set equality261096.3%100.0%98.1%

The cliff sits between 0.95 and 1.0, and everything falling off it is React. Inside a framework, two different handlers still share almost every function they execute — the synthetic event system, the scheduler, the reconciler — so a broken <div onClick> and a correct <button onClick> measure 0.95 similar while doing entirely different things. Any tolerant threshold silently deletes real defects.

Subtracting a per-page baseline helps and is worth doing — clicking a handler-free target first, then removing those functions from every subsequent set, stripped 28 functions per click from the React page. It was not enough on its own. Require exact set equality, and take the baseline subtraction as well.

What this means for the crawler

The candidate generator this repo ships today — collectClickables in lib/crawler/scanner.ts — scores 3.8% recall at 33.3% precision here. That is expected: it was written to find things worth clicking during a crawl, not to find keyboard defects, and it is measured out of scope. Two findings do apply to it as it stands.

Its selectors are ambiguous. The tag.class1.class2 strings it emits matched more than one element 8 times out of 14 on this corpus. Because the crawl clicks .first(), every collision is a control it believes it has visited and has not. That is a live bug in coverage, independent of anything in the survey.

Its click oracle is the weakest one measured. The innerHTML hash comparison in scanInteractiveElements is exactly the “DOM only” row: 80.8% recall, blind to any handler whose effect is a fetch, a storage write, a canvas draw, or a CSS-only reveal. Those clicks are currently logged as no DOM change — skipping. Adding the geometry channel alone recovers CSS-only reveals for one extra getComputedStyle pass per snapshot.

Threats to validity

  • Synthetic corpus, built from the survey's own examples. Every defect here is one the survey predicted. Real pages contain defect shapes nobody listed, and the recall figures should be read as an upper bound.
  • Same author for fixtures and detectors. Ground truth was written and committed before any detector was scored, but the fixtures were not authored blind.
  • n = 26 positives. One probe moves recall by 3.8 points. Differences under about 8 points between adjacent rows are not meaningful.
  • One engine, one viewport. Chromium at 1280×900. Hover menus and responsive collapse are viewport-dependent, so single-resolution results undercount — the same limitation the survey notes of KAFE's fixed 1920×1080.
  • Runtimes are single-run, not benchmarks. They moved 10–80% between otherwise identical runs on a loaded machine. Read them as orders of magnitude: the prefilters are milliseconds, the oracle is seconds per probe.
  • React 19 only. The el.onclick finding is specific to this version and may not hold for React 17/18, Vue, or Angular.
  • Fixture handlers share a helper. All probes call the same fired() function, which inflates coverage overlap between unrelated handlers and makes the Stage-4 threshold result, if anything, pessimistic.
